# 合成方式とバッチ実行

## 入力と固定条件

日本語2話者の台本を1対話1 JSONLにします。

```jsonl
["A", "こんにちは。"]
["B", "今日は何を話しましょうか。"]
```

A=S1=左、B=S2=右です。生成条件は台本件数やGPU数に依存しません。

| 項目 | 標準条件 |
| --- | --- |
| TTS | llm-jp/zoom1-dialogue-tts / drop |
| TTS revision | aa9ad6cb9b03588deaeeb1c0611d455317855776 |
| 生成 | seed 1を対話ごとに設定、temperature 0.8、top-k 20、BF16 |
| S1参照 | references/turn000_S1.wav |
| 参照文 | こんにちは、最近の物価についてどう思いますか？ |
| 参照範囲 | 最初のS1ターンだけ。後続は生成履歴 |
| 通常ターンVAP | maai-kyoto/vap_jp_kyoto / fe24ac60d8fcc80463edde97ed90e3ceca5e5b88 |
| 台本内相槌VAP | maai-kyoto/vap_bc_jp / 309d7936f5a929870e3e02a563729b7dc8b78a6e |
| MaAI | 0.2.13 |
| 元ターン音声 | 24 kHz mono PCM16 |
| VAP解析音声 | 16 kHz stereo、台本内相槌自身を除いた逐次配置 |
| 完成音声 | 24 kHz stereo、S1=左、S2=右 |

参照ファイルのSHA-256は `c474f09ccd384bc4a6fa9e3af19564fed45751f26f4f0a5c83fc5061bc055d81`。
参照音声を使う標準実行は、このリポジトリのチェックアウトから行ってください。
参照音声・FT重み・入力台本の利用条件は、それぞれの許諾に従います。
VAPのMITライセンスだけで全体の商用利用可否が確定するわけではありません。

## 実行と再開

READMEのTTS環境と別のMaAI環境を準備してから実行します。

```bash
uv run zoom1-dialogue-tts inputs/dialogue.jsonl -o dialogues/dialogue.wav \
  --vap-python .venv-vap/bin/python
```

CPU/GPUのVAP実行先は `--vap-device cpu` / `cuda` で変更できます。
BF16に対応しないGPUでは停止します。別の精度の実験は `--dtype float32` を明示します。
S1参照は既存の同梱音声を使います。S2参照は指定しません。

1. ターンをGPU上で生成。履歴の音声トークンを一度だけ作り再利用。
2. 対話生成完了後にCPUへ移し、`dialogues/dialogue_turns/` に全WAVとmanifestを確定。
3. 相槌を除いた16 kHz解析音声をCPUで作成。
4. Kyoto VAPと相槌VAPでスコアを推論。相槌がなければ相槌モデルは使わない。
5. 元ターンWAVをCPUで時間配置し、完成WAVと開始時刻・参照元・使用モデルのmanifestを保存。

ターンmanifestは台本ハッシュ、参照音声ハッシュ、モデルrevision、生成条件、各ターンの
話者・文・サンプル数・長さ・削除した履歴数を保持します。
同じコマンドの再実行は、設定とWAVの形式・サンプル数を検証して元ターンを再利用し、配置をやり直します。
既存ターンが不完全／別設定なら停止します。調査して別の場所に保管してから再生成してください。
`--final-only` を明示しても元ターンとそのmanifestは保存し続けます。

通常ターンはSHIFT/HOLDスコアから配置し、短い割り込み相槌は台本上のアンカー前後0.6秒で
`p_bc`のピークへ配置します。左右を入れ替えた相槌解析も実施します。
配置に使わないreact/emoタイプ分類は標準では実行しません。
新しい相槌音声を追加する実験だけ `--backchannels stat` / `vap` を指定します。

## 計算資源と大規模処理

リソース数は運用条件です。入力件数N、ノード数J、GPU数G、プロセス/GPU Pならワーカー数はJ×G×P。
台本一覧から件数・総ターン数を数え、総ターン数を均すようにTTS担当リストを作成します。
VAPでは生成後の総音声長で負荷分散します。固定の対話件数を検証対象数に使わないでください。
空ファイル、空発話、不明な話者、2話者が揃うことをCPUで検査します。

短い・長い・相槌を含む台本で、1/2/4、必要なら8プロセス/GPUを比較します。
TTSとVAPは別々に測り、モデルロード込みの完了壁時計時間、処理音声長、GPUメモリを記録します。
過去のTTS 2/GPU・VAP 4/GPUは測定例です。他の台本やGPUへ無条件に適用しません。
スモークで成功した元ターンは同じ本番出力先で再利用します。

`--batch SCRIPT OUTPUT` を繰り返すとTTSモデルを一度だけロードできます。
多数の対話では `bc_cli` の `--server SOCKET` と `ZOOM1_MAAI_SOCKET` を使うことで
VAPモデルも保持できます。サーバーの既定モデルはbcとKyoto VAPです。
共有環境では各ワーカーに専用ソケットを割り当てます。

PBS等で工程を分ける場合の順序:

```text
入力検査・担当一覧（CPU）
→ 小規模TTS（GPU）→ 全件検証（CPU）
→ 残りのTTS（GPU）→ 全件検証（CPU）
→ VAP入力準備（CPU）→ VAPスコア推論（GPU）
→ 完成WAV組み立て（CPU）→ 全件検証（CPU）
```

段階数は件数と許容リスクに応じて決めます。後続PBSジョブに
`depend=afterok:<先行ID>`、複数ジョブを待つ場合は `afterok:<ID1>:<ID2>` を指定します。
検証は担当一覧の全入力について欠落・WAV形式・長さ・manifestとの一致を調べ、不備があれば非zero終了します。

GPU確保前に入力探索・検証とモデルキャッシュの準備を済ませ、ジョブ開始時にモデルと担当入力を
ノードローカルへコピーします。ポイント概算は「各ノードの予想時間の合計×ポイント単価」です。
総ターン数・総音声長とスモークの実測速度から予想時間を計算します。

このCLIは対話ごとの生成と配置をまとめて実行します。上のPBS工程分離は運用指針であり、
サイト固有のPBSグループやノード構成を自動投入するスクリプトは含めていません。
